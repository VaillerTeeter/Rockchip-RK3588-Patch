# Rockchip U-Boot 调试手段

本章系统介绍 U-Boot 阶段常用的调试手段，涵盖调试打印、命令行工具、配置选项、开机信息分析等方面，帮助开发者快速定位和解决 U-Boot 及启动流程中的问题。

> **说明**：全文所有章节中提到的开启/关闭 `CONFIG_` 配置项，均指通过 `make menuconfig` 方式操作。请勿直接在 `defconfig` 中手动修改 `CONFIG_` 配置项，避免因 Kconfig 依赖关系导致 `.config` 不生效。

## 一、DEBUG 调试打印

**功能**：使能全局 `debug()` 打印输出。

在各平台的 `rkxxx_common.h` 中增加宏定义即可使能：

```
#define DEBUG
```

> 使能后，U-Boot 启动过程中所有调用 `debug()` 的地方都会输出调试信息，可帮助追踪详细的代码执行流程。

## 二、Initcall 启动流程追踪

**功能**：打印启动流程中的 initcall 调用序列。

U-Boot 的启动实质是一系列 initcall 调用，将 `initcall_run_list()` 函数内的 `debug()` 改为 `printf()` 即可打印完整的调用序列。

**代码位置**：`./lib/initcall.c`

**范例输出**：

```
U-Boot 2017.09-01725-g03b8d3b-dirty (Jul 06 2018 - 10:08:27 +0800)
initcall: 0000000000214388
initcall: 0000000000214724
Model: Rockchip RK3399 Evaluation Board
initcall: 0000000000214300
DRAM: initcall: 0000000000203f68
initcall: 0000000000214410     // 结合反汇编找出地址对应的函数
initcall: 00000000002140dc
....
3.8 GiB
initcall: 00000000002143b8
....
Relocation Offset is: f5c03000
initcall: 00000000f5e176bc
initcall: 00000000002146a4 (relocated to 00000000f5e176a4)
initcall: 0000000000214668 (relocated to 00000000f5e17668)
...
```

> 打印的地址可通过 `./make.sh <addr>` 命令反查对应的函数名，详见"平台架构"章节的 Make.sh 调试工具部分。

## 三、io 命令（内存读写）

**功能**：直接读写内存/寄存器，是 U-Boot 下最基础的硬件调试手段。

### 3.1 读操作（md）

```
md - memory display
Usage: md [.b, .w, .l, .q] address [# of objects]
```

**范例**：显示 `0x76000000` 地址开始的连续 `0x10` 个 32 位数据：

```
=> md.l 0x76000000 0x10
76000000: fffffffe ffffffff ffffffff ffffffff ................
76000010: ffffffdf ffffffff feffffff ffffffff ................
76000020: ffffffff ffffffff ffffffff ffffffff ................
76000030: ffffffff ffffffff ffffffff ffffffff ................
```

### 3.2 写操作（mw）

```
mw - memory write (fill)
Usage: mw [.b, .w, .l, .q] address value [count]
```

**范例**：对 `0x76000000` 地址赋值为 `0xffff1234` 并回读验证：

```
=> mw.l 0x76000000 0xffff1234      // 高 16 位有 mask
=> md.l 0x76000000 0x10            // 回读确认
76000000: ffff1234 ffffffff ffffffff ffffffff ................
76000010: ffffffdf ffffffff feffffff ffffffff ................
76000020: ffffffff ffffffff ffffffff ffffffff ................
76000030: ffffffff ffffffff ffffffff ffffffff ................
```

> **注意**：部分寄存器的高位可能有硬件 mask 限制，写入的值不一定完全等于回读的值。`.b` / `.w` / `.l` / `.q` 分别对应 8 / 16 / 32 / 64 位访问宽度。

## 四、iomem 命令（寄存器便捷读取）

**功能**：通过自动解析 DTS 节点获取外设基地址，比 `md` 命令更便捷，无需手动查找寄存器基地址。

```
=> iomem
iomem - Show iomem data by device compatible

Usage:
iomem <compatible> <start offset> <end offset>
```

> `<compatible>` 为 DTS 节点 `compatible` 属性的关键词匹配，`<start offset>` 和 `<end offset>` 为相对于基地址的偏移量。

**范例**：RK3228 平台读取 GRF 模块 `0x00 ~ 0x20` 的寄存器值：

```
// 使用 "-grf" 作为关键词，与 "rockchip,rk3288-pmugrf" 区分
=> iomem -grf 0x0 0x20
rockchip,rk3228-grf:
11000000: 00000000 00000000 00004000 00002000
11000010: 00000000 00005028 0000a5a5 0000aaaa
11000020: 00009955
```

## 五、i2c 命令（I2C 设备读写）

**功能**：读写 I2C 总线上的外设寄存器（如 PMIC、触摸屏、传感器等）。

```
=> i2c
i2c - I2C sub-system

Usage:
i2c dev [dev]                                     - show or set current I2C bus
i2c md chip address[.0, .1, .2] [# of objects]    - read from I2C device
i2c mw chip address[.0, .1, .2] value [count]     - write to I2C device (fill)
......
```

> `address[.0, .1, .2]` 中的后缀表示寄存器地址宽度：`.0` = 0 字节（无地址），`.1` = 1 字节（默认），`.2` = 2 字节。

### 5.1 读操作

```
=> i2c dev 0                        // 切换到 i2c0 总线（只需指定一次）
Setting bus to 0

=> i2c md 0x1b 0x2e 0x20            // 设备地址 0x1b（7 位），读取 0x2e 开始的连续 0x20 个寄存器
002e: 11 0f 00 00 11 0f 00 00 01 00 00 00 09 00 00 0c ................
003e: 00 0a 0a 0c 0c 0c 00 07 07 0a 00 0c 0c 00 00 00 ................
```

### 5.2 写操作

```
=> i2c dev 0                        // 切换到 i2c0 总线
Setting bus to 0

=> i2c mw 0x1b 0x2e 0x10            // 设备地址 0x1b，向 0x2e 寄存器写入 0x10
=> i2c md 0x1b 0x2e 0x20            // 回读验证
002e: 10 0f 00 00 11 0f 00 00 01 00 00 00 09 00 00 0c ................
003e: 00 0a 0a 0c 0c 0c 00 07 07 0a 00 0c 0c 00 00 00 ................
```

## 六、gpio 命令（GPIO 控制）

**功能**：查询和控制 GPIO 引脚的输入输出状态，用于调试板级外设。

```
=> gpio
gpio - query and control gpio pins

Usage:
gpio <input|set|clear|toggle> <pin>          - input/set/clear/toggle the specified pin
gpio status [-a] [<bank> | <pin>]            - show [all/claimed] GPIOs
```

### 6.1 查看引脚状态（以 RV1126 为例）

```
=> gpio status -a
Bank A:
A0: input: 0 [ ]
A1: output: 1 [ ]
A2: input: 1 [ ]
...
A29: unused: 1 [ ]
A30: unknown
A31: unused: 0 [ ]
...
D6: input: 0 [ ]
D7: output: 1 [x] vcc18-lcd-n.gpio
...
D31: input: 0 [ ]

Bank E:
E0: input: 0 [ ]
E1: input: 0 [ ]
```

> `[x]` 标记表示该 GPIO 已被驱动占用，`[ ]` 表示空闲。

### 6.2 操作引脚

| 操作 | 命令 | 说明 |
|------|------|------|
| 读取输入 | `gpio input A7` | 读取 A7 引脚的输入电平 |
| 输出低电平 | `gpio clear A7` | 设置 A7 输出 INACTIVE |
| 输出高电平 | `gpio set A7` | 设置 A7 输出 ACTIVE |
| 翻转状态 | `gpio toggle A7` | 如 `A7: input: 0` → `A7: output: 1` |

## 七、fdt 命令（DTB 查看）

**功能**：查看设备树（DTB）内容，确认节点和属性是否正确。

```
=> fdt
fdt - flattened device tree utility commands

Usage:
fdt addr [-c] <addr> [<length>]   - Set the [control] fdt location to <addr>
fdt print <path> [<prop>]         - Recursive print starting at <path>
fdt list <path> [<prop>]          - Print one level starting at <path>
......
NOTE: Dereference aliases by omitting the leading '/', e.g. fdt print ethernet0.
```

**常用组合**：完整 dump 出当前 DTB 的全部内容：

```
=> fdt addr $fdt_addr_r            // 指定 FDT 地址
=> fdt print                       // 打印全部 DTB 内容
```

> DTO 操作后可配合 `fdt` 命令验证设备树叠加是否生效。详见"系统模块"章节的 DTBO/DTO 部分。

## 八、mmc 命令（MMC 设备操作）

**功能**：查看、切换、读写 MMC 设备（eMMC / SD 卡）。

### 8.1 设备信息查看

```
=> mmc info
Device: dwmmc@ff0f0000              // 设备节点
Manufacturer ID: 15
OEM: 100
Name: 8GME4
Timing Interface: High Speed        // 速度模式
Tran Speed: 52000000                // 当前速率
Rd Block Len: 512
MMC version 5.1
High Capacity: Yes
Capacity: 7.3 GiB                   // 存储容量
Bus Width: 8-bit                    // 总线宽度
Erase Group Size: 512 KiB
HC WP Group Size: 8 MiB
User Capacity: 7.3 GiB WRREL
Boot Capacity: 4 MiB ENH
RPMB Capacity: 512 KiB ENH
```

### 8.2 设备切换

```
=> mmc dev 0            // 切换到 eMMC
=> mmc dev 1            // 切换到 SD 卡
```

### 8.3 设备读写

```
mmc read addr blk# cnt
mmc write addr blk# cnt
mmc erase blk# cnt
```

**范例**：

```
=> mmc read 0x70000000 0 1     // 读取第 0 个 block（1 sector）到内存 0x70000000
=> mmc write 0x70000000 0 1    // 将内存 0x70000000 起 1 sector 数据写入第 0 个 block
=> mmc erase 0 1               // 擦除第 0 个 block 起 1 sector 数据
```

### 8.4 读写异常定位

如果 MMC 设备读写异常，将 `drivers/mmc/dw_mmc.c` 内的 `debug()` 改为 `printf()` 后重新编译烧写，根据打印信息定位：

| 最后的打印 | 可能原因 | 排查方向 |
|-----------|----------|----------|
| `Sending CMD0` | 硬件连接或 IOMUX 问题 | 检查硬件供电、管脚连接；检查 IOMUX 是否被其他 IP 切换 |
| `Sending CMD8` | 安全存储访问限制 | 安全软件部分需配置 MMC 设备允许访问安全存储 |
| `Sending CMD18` | 初始化通过但读写异常 | 检查供电、靠近 MMC 供电端的电容是否足够（可更换大电容）；降低时钟频率；切换速度模式 |

## 十、dm tree（设备驱动树）

**功能**：查看所有 device-driver 之间的绑定和 probe 状态，是分析设备驱动加载问题的核心工具。

```
=> dm tree

 Class     Probed  Driver                        Name
----------------------------------------------------------
 root      [ + ]   root_driver                   root_driver
 syscon    [   ]   rk322x_syscon                 |-- syscon@11000000
 serial    [ + ]   ns16550_serial                |-- serial@11030000 *
 clk       [ + ]   clk_rk322x                    |-- clock-controller@110e0000
 sysreset  [   ]   rockchip_sysreset             | |-- sysreset
 reset     [   ]   rockchip_reset                | `-- reset
 mmc       [ + ]   rockchip_rk3288_dw_mshc       |-- dwmmc@30020000 *
 blk       [ + ]   mmc_blk                       | `-- dwmmc@30020000.blk *
 ram       [   ]   rockchip_rk322x_dmc           |-- dmc@11200000
 serial    [ + ]   ns16550_serial                |-- serial@11020000
 i2c       [ + ]   i2c_rockchip                  |-- i2c@11050000
 ......
```

**符号含义**：

| 符号 | 含义 |
|------|------|
| `[ + ]` | 当前 driver 已完成 probe |
| `[   ]` | 已完成 bind，但尚未 probe |
| `*` | 设备来源于 U-Boot DTB（否则来源于 Kernel DTB） |
| `├` / `└` / `│` / `\`` | 表示 uclass-device-driver 之间的隶属层级关系 |

## 十二、stacktrace.sh（调用栈回溯）

**功能**：利用调用栈回溯机制，将系统 abort 或 `dump_stack()` 的现场地址转换为可读的函数名和代码位置。

> 调用栈回溯的原理和触发方式请参考"平台架构"章节的"调用栈回溯"部分。

**使用方法**：

将 Call trace 信息复制到任意 txt 文件（如 `dump.txt`），然后执行：

```
./scripts/stacktrace.sh ./dump.txt       # 解析来自 U-Boot 的调用栈
./scripts/stacktrace.sh ./dump.txt tpl   # 解析来自 TPL 的调用栈
./scripts/stacktrace.sh ./dump.txt spl   # 解析来自 SPL 的调用栈
```

> **注意**：执行该命令时，当前机器上的固件必须和当前代码环境匹配，否则会得到错误的转换结果。

## 十三、系统卡死调试（CONFIG_ROCKCHIP_DEBUGGER）

**功能**：当系统卡死时，串口每隔 5s 自动 dump 出当前 CPU 的现场和调用栈信息（与 abort 时类似）。

```
CONFIG_ROCKCHIP_DEBUGGER
```

获取到调用栈信息后，再使用 stacktrace 脚本进行转换（参见第十二节）。

## 十六、修改 DDR 容量

**功能**：在 U-Boot 阶段调整传递给内核的 DDR 可用容量，用于调试内存相关问题。

### 16.1 传递范例

```
......
// 传递给内核的可用内存块（已去除安全内存块）。
Adding bank: 0x00200000 - 0x08400000 (size: 0x08200000)
Adding bank: 0x0a200000 - 0x40000000 (size: 0x35e00000)
Total: 895.411 ms
Starting kernel ...
```

### 16.2 代码位置与修改方法

**代码位置**：`./arch/arm/mach-rockchip/param.c`

**核心函数**：`param_parse_ddr_mem()`

```
struct memblock *param_parse_ddr_mem(int *out_count)
{
    ......
    // DDR 传递给 U-Boot 的容量信息
    // 可能出现不连续的地址，会分块传递，分别指明各内存块的起始地址和大小
    // 一般情况下都是连续内存，不需要分块
    for (i = 0, n = 0; i < count; i++, n++) {
        // 比如 2GB 容量（连续地址），则：count=1, base=0, size=0x80000000
        // 用户调试时可以在此按需修改
        base = t->u.ddr_mem.bank[i];
        size = t->u.ddr_mem.bank[i + count];

        /* 0~4GB */
        if (base < SZ_4GB) {
            mem[n].base = base;
            mem[n].size = ddr_mem_get_usable_size(base, size);
            if (base + size > SZ_4GB) {
                n++;
                mem[n].base_u64 = SZ_4GB;
                mem[n].size_u64 = base + size - SZ_4GB;
            }
        } else {
            /* 4GB+ */
            mem[n].base_u64 = base;
            mem[n].size_u64 = size;
        }

        assert(n < count + MEM_RESV_COUNT);
    }
    ......
}
```

> 调试时可在上述 `base` / `size` 的赋值处按需修改传递给内核的内存容量，用于排查内存相关异常。

## 十七、跳转信息与版本回溯

**功能**：通过 Trust 和 U-Boot 的开机打印确认固件版本、跳转地址和编译状态，帮助定位死机原因。

### 17.1 Trust 跳转地址确认

Trust 阶段跑完后卡死的常见原因：固件打包或烧写有误，导致 Trust 跳转到错误的 U-Boot 启动地址。通过 Trust 的开机打印可确认跳转地址。

**64 位平台**（U-Boot 启动地址一般为 DDR 基地址偏移 `0x200000`）：

```
NOTICE: BL31: v1.3(debug):d98d16e
NOTICE: BL31: Built : 15:03:07, May 10 2018
NOTICE: BL31: Rockchip release version: v1.1
INFO: GICv3 with legacy support detected. ARM GICV3 driver initialized in EL3
INFO: Using opteed sec cpu_context!
INFO: boot cpu mask: 0
INFO: plat_rockchip_pmu_init(1151): pd status 3e
INFO: BL31: Initializing runtime services
INFO: BL31: Initializing BL32
INFO: BL31: Preparing for EL3 exit to normal world
INFO: Entry point address = 0x200000       // U-Boot 启动地址
INFO: SPSR = 0x3c9
```

**32 位平台**（U-Boot 启动地址一般为 DDR 基地址偏移 `0x0`，DDR 基地址 = `0x60000000`）：

```
INF [0x0] TEE-CORE:init_primary_helper:378: Release version: 1.9
INF [0x0] TEE-CORE:init_primary_helper:379: Next entry point address: 0x60000000   // U-Boot 启动地址
INF [0x0] TEE-CORE:init_teecore:83: teecore inits done
```

| 平台 | U-Boot 启动地址（相对 DDR base） | 范例 |
|------|-------------------------------|------|
| 64 位 | `0x200000` | `Entry point address = 0x200000` |
| 32 位 | `0x0`（DDR base = `0x60000000`） | `Next entry point address: 0x60000000` |

### 17.2 U-Boot 版本回溯

通过 U-Boot 开机信息可回溯编译版本：

```
// 正常版本：对应 commit b34f08b
U-Boot 2017.09-01730-gb34f08b (Jul 06 2018 - 17:47:52 +0800)

// dirty 版本：编译时有本地改动未提交
U-Boot 2017.09-01730-gb34f08b-dirty (Jul 06 2018 - 17:35:04 +0800)
```

> 开机信息中出现 `-dirty` 说明编译点不干净，有本地改动未提交进仓库，该版本不具备版本回溯的可靠性。

## 十八、启动信息分析

**功能**：通过 U-Boot 开机信息了解当前启动流程和各外设状态，快速定位异常。

目前 U-Boot 支持三种固件类型引导，优先级为：**Android 格式 > RK 格式 > Distro 格式**。RK 发布的 SDK 主要使用前两种格式，Distro 格式一般由开源用户使用。

> 说明：如果代码版本不够新，部分打印可能不可见，不影响对 U-Boot 开机信息的整体理解。

### 18.1 Android 固件


### 18.5 启动异常快速定位指南

| 异常现象 | 快速定位方向 |
|---------|-------------|
| Trust 打印后卡死，无 U-Boot 打印 | 检查 Trust 跳转地址（第十七节），确认固件打包正确 |
| U-Boot 打印后卡死 | 开启 DEBUG（第一节）和时间戳（第九节），定位最后执行的 initcall |
| `Starting kernel ...` 打印后无内核输出 | 检查 Kernel 加载地址和 DTB 内容（第七节），确认 Cmdline 配置（参考"系统模块"章节） |
| MMC 读写异常 | 参考第八节读写异常定位表 |
| 系统随机崩溃 | 开启 CONFIG_ROCKCHIP_DEBUGGER（第十三节），结合 stacktrace（第十二节）分析 |
| 固件完整性疑惧 | 开启 CRC 校验（第十四节）或 HASH 校验（第十五节） |
| 内存容量异常 | 检查 DDR 容量传递（第十六节），确认安全内存是否被过多预留 |
