# Rockchip U-Boot 平台架构

本章介绍 Rockchip 平台 U-Boot 的基础架构、核心机制和重要特性。

## 一、开发环境与配置

### 1.1 平台文件

平台源码目录：

```
./arch/arm/include/asm/arch-rockchip/
./arch/arm/mach-rockchip/
./board/rockchip/
./include/configs/
```

`defconfig` 目录：

```
./configs/
```

核心公共板级文件：

```
./arch/arm/mach-rockchip/board.c
```

### 1.2 平台配置

各平台的配置选项、参数通常位于以下几个位置：

```
// 各平台公共文件（开发者通常不需要修改）
./arch/arm/mach-rockchip/Kconfig
./include/configs/rockchip-common.h

// 各平台独有配置，以 RK3399 为例
./include/configs/rk3399_common.h
./include/configs/evb_rk3399.h
./configs/rk3399_defconfig
```

以下针对 `rockchip-common.h`、`rkxxx_common.h`、`evb_rkxxx.h` 中定义的重要配置项给出说明：

| 配置项 | 说明 |
|--------|------|
| `RKIMG_DET_BOOTDEV` | 存储类型探测命令，以逐个扫描的方式探测当前的存储设备类型 |
| `RKIMG_BOOTCOMMAND` | Kernel 启动命令 |
| `ENV_MEM_LAYOUT_SETTINGS` | 固件加载地址，包括 ramdisk / fdt / kernel |
| `PARTS_DEFAULT` | 默认 GPT 分区表，当存储中未发现有效 GPT 分区表时使用 |
| `ROCKCHIP_DEVICE_SETTINGS` | 外设相关命令，主要用于指定 stdio（一般包含显示模块启动命令） |
| `BOOTENV` | Distro 方式启动 Linux 时的启动设备探测命令 |
| `CONFIG_SYS_MALLOC_LEN` | malloc 内存池大小 |
| `CONFIG_SYS_TEXT_BASE` | U-Boot 运行的起始地址 |
| `CONFIG_BOOTCOMMAND` | 启动命令，一般定义为 `RKIMG_BOOTCOMMAND` |
| `CONFIG_PREBOOT` | 预启动命令，在 `CONFIG_BOOTCOMMAND` 之前被执行 |
| `CONFIG_SYS_MMC_ENV_DEV` | MMC 作为 ENV 存储介质时的 dev num，一般是 0 |

### 1.3 Make.sh 编译与调试工具

`make.sh` 既是一个编译脚本，也是一个打包和调试工具，可用于反汇编和固件打包。

**打包固件：**

```
./make.sh trust            # 打包 trust
./make.sh loader           # 打包 loader
./make.sh trust <ini-file> # 打包 trust 时指定 ini 文件
./make.sh loader <ini-file># 打包 loader 时指定 ini 文件
./make.sh spl              # 用 TPL+SPL 替换 DDR Bin 和 Miniloader，打包成 Loader
./make.sh spl-s            # 用 SPL 替换 Miniloader，打包成 Loader
./make.sh itb              # 打包 u-boot.itb（64 位平台只支持打包 ATF 和 U-Boot，OP-TEE 不打包）
./make.sh env              # 生成 fw_printenv 工具
```

**反汇编与调试：**

```
./make.sh elf-[x] [type]   # 反汇编：使用 -[x] 参数，[type] 可选择是否反汇编 SPL 或 TPL
./make.sh elf              # 反汇编 u-boot 文件，默认使用 -D 参数
./make.sh elf-S            # 反汇编 u-boot 文件，使用 -S 参数
./make.sh elf-d            # 反汇编 u-boot 文件，使用 -d 参数
./make.sh elf spl          # 反汇编 SPL，默认使用 -D 参数
./make.sh elf tpl          # 反汇编 TPL，默认使用 -D 参数
./make.sh <addr>           # 查询 addr 对应的函数名和代码位置
./make.sh map              # 打开 u-boot.map
./make.sh sym              # 打开 u-boot.sym
```

## 二、启动流程

### 2.1 完整启动顺序

Rockchip 平台 U-Boot 的启动流程如下，以下仅列出重要步骤：

```
start.s
    // 汇编环境
    => IRQ/FIQ/lowlevel/vbar/errata/cp15/gic     // ARM 架构相关的 lowlevel 初始化
    => _main
    => stack // 准备好 C 环境需要的栈

    // 【第一阶段】C 环境初始化，发起一系列函数调用
    => board_init_f: init_sequence_f[]
        initf_malloc
        arch_cpu_init                            // 【SoC 的 lowlevel 初始化】
        serial_init                              // 串口初始化
        dram_init                                // 【获取 DDR 容量信息】
        reserve_mmu                              // 从 DDR 末尾开始往低地址 reserve 内存
        reserve_video
        reserve_uboot
        reserve_malloc
        reserve_global_data
        reserve_fdt
        reserve_stacks
        dram_init_banksize
        sysmem_init
        setup_reloc                              // 确定 U-Boot 自身要 reloc 的地址

    // 汇编环境
    => relocate_code                             // 汇编实现 U-Boot 代码的 relocation

    // 【第二阶段】C 环境初始化，发起一系列函数调用
    => board_init_r: init_sequence_r[]
        initr_caches                             // 使能 MMU 和 I/D Cache
        initr_malloc
        bidram_initr
        sysmem_initr
        initr_of_live                            // 初始化 of_live
        initr_dm                                 // 初始化 DM 框架
        board_init                               // 【平台初始化，最核心部分】
            board_debug_uart_init                // 串口 iomux、clk 配置
            init_kernel_dtb                      // 【切换到 Kernel DTB】
            clks_probe                           // 初始化系统频率
            regulators_enable_boot_on            // 初始化系统电源
            io_domain_init                       // io-domain 初始化
            set_armclk_rate                      // __weak，ARM 提频（平台有需求才实现）
            dvfs_init                            // 宽温芯片的调频调压
            rk_board_init                        // __weak，由各个具体平台实现
        console_init_r
        board_late_init                          // 【平台 late 初始化】
            rockchip_set_ethaddr                 // 设置 MAC 地址
            rockchip_set_serialno                // 设置 Serial No
            setup_boot_mode                      // 解析 "reboot xxx" 命令、识别按键和 Loader 烧写模式
            recovery
            charge_display                       // U-Boot 充电
            rockchip_show_logo                   // 显示开机 Logo
            soc_clk_dump                         // 打印 CLK Tree
            rk_board_late_init                   // __weak，由各个具体平台实现
        run_main_loop                            // 【进入命令行模式，或执行启动命令】
```

### 2.2 代码重定位（Relocation）

U-Boot 会在完成 `board_f.c` 流程后，将自己重定位（Relocate）到内存末尾的某个地址上，具体地址视 U-Boot 内存布局而定。

Rockchip U-Boot 默认：

- **32 位平台**：`CONFIG_SKIP_RELOCATE_UBOOT=y` 时不做 relocation，否则会做
- **64 位平台**：始终进行 relocation

## 三、内存管理

### 3.1 内存布局

U-Boot 由前级 Loader 加载到 `CONFIG_SYS_TEXT_BASE` 地址，初始化时会探明当前系统的总内存容量：

- 32 位平台上认为最大 4GB 可用（不影响内核对容量的识别）
- 64 位平台上认为所有内存都可用

然后通过一系列 `reserve_xxx()` 接口从内存末尾往前预留需要的内存，最后把自己 Relocate 到某段预留的空间上。

内存整体使用布局如下（以 ARM64 常规情况为例）：

| 区域 | 起始地址偏移 | 大小 | 用途 | Secure |
|------|------------|------|------|--------|
| ATF | 0x00000000 | 1M | ARM Trusted Firmware | Yes |
| SHM | 0x00100000 | 1M | SHM, Pstore | No |
| OP-TEE | 0x08400000 | 2M ~ 30M | 参考 TEE 开发手册 | Yes |
| FDT | fdt_addr_r | - | Kernel DTB | No |
| KERNEL | kernel_addr_r | - | Kernel 镜像 | No |
| RAMDISK | ramdisk_addr_r | - | Ramdisk 镜像 | No |
| …… | - | - | - | - |
| FASTBOOT | - | - | Fastboot buffer | No |
| …… | - | - | - | - |
| SP | - | - | Stack | No |
| FDT | - | sizeof(dtb) | U-Boot DTB | No |
| GD | - | sizeof(gd) | Global Data | No |
| Board | - | sizeof(bd_t) | Board Data | No |
| MALLOC | - | CONFIG_SYS_MALLOC_LEN | 系统堆空间 | No |
| U-Boot | - | sizeof(mon) | U-Boot 镜像 | No |
| Video FB | - | fb size（~32M） | 显存 | No |
| TLB Table | RAM_TOP - 64K | 32K | MMU 页表 | No |

> **说明**：
> - 上表中"起始地址偏移"为基于 DDR base 的偏移量
> - Fastboot 地址和大小由 `CONFIG_FASTBOOT_BUF_ADDR`、`CONFIG_FASTBOOT_BUF_SIZE` 决定
> - Video FB / U-Boot / Malloc / Board / GD / FDT / SP 由顶向下根据实际需求大小分配
> - 64 位平台：ATF 是 ARMv8 必需的，OP-TEE 是可选项；32 位平台：只有 OP-TEE
> - Kernel DTB / Kernel / Ramdisk 是 U-Boot 需要加载的固件地址，由 `ENV_MEM_LAYOUT_SETTINGS` 定义
> - OP-TEE 占据的空间根据实际需求而定，最大 30M；RK1808 / RK3308 上 OP-TEE 放在低地址，不在 0x08400000

### 3.2 Bidram / Sysmem

U-Boot 可以使用系统的所有内存，且从高地址往低地址预留系统所需的内存，预留完后通常还剩余较大的内存空间。U-Boot 原生没有机制管理这块空间，因此 Rockchip 平台引入 **bidram** 和 **sysmem** 内存块机制进行管理。

由此，加上 U-Boot 已有的 malloc 管理机制，Rockchip 平台把所有系统内存通过 **sysmem + bidram + malloc** 统一管理，防止内存冲突。

```
低地址                                                     高地址
|-----------------------------------------------------------|-----------------|
|                     no management                         |   system used   |
|-----------------------------------------------------------|-----------------|
0x0                                                         N GB
```

- **bidram**：管理 U-Boot、Kernel 阶段不可用、需要剔除的内存块（例如 ATF、OP-TEE 占用的空间）
- **sysmem**：管理 Kernel 可见、可用的内存块（例如 FDT、Ramdisk、Kernel、Fastboot 占用的空间）

**相关代码**：

```
./lib/sysmem.c
./lib/bidram.c
./include/memblk.h
./arch/arm/mach-rockchip/memblk.c
```

#### bidram 内存信息表

当出现内存块初始化或分配异常时，会 dump 出 bidram 信息表：

```
bidram_dump_all:
    --------------------------------------------------------------------
    // <1> U-Boot 从前级 Loader 获取的 DDR 总容量信息，共 2GB
    memory.rgn[0].addr = 0x00000000 - 0x80000000 (size: 0x80000000)

    memory.total = 0x80000000 (2048 MiB. 0 KiB)
    --------------------------------------------------------------------
    // <2> 被预留起来的各固件内存信息，这些空间对 Kernel 不可见
    reserved.rgn[0].name = "ATF"
                   .addr = 0x00000000 - 0x00100000 (size: 0x00100000)
    reserved.rgn[1].name = "SHM"
                   .addr = 0x00100000 - 0x00200000 (size: 0x00100000)
    reserved.rgn[2].name = "OP-TEE"
                   .addr = 0x08400000 - 0x0a200000 (size: 0x01e00000)

    reserved.total = 0x02000000 (32 MiB. 0 KiB)
    --------------------------------------------------------------------
    // <3> 核心算法对 <2> 进行的预留信息整理（对相邻块进行合并）
    LMB.reserved[0].addr = 0x00000000 - 0x00200000 (size: 0x00200000)
    LMB.reserved[1].addr = 0x08400000 - 0x0a200000 (size: 0x01e00000)

```

#### 常见错误分析

以下是一些常见的错误打印，请结合 bidram 和 sysmem dump 信息进行分析：

```
// 期望申请的内存已被其他固件占用，存在内存重叠——当前系统内存规划不合理

Sysmem Error: Failed to double alloc for existence "RAMDISK"

## 四、存储与分区

### 4.1 存储布局

Rockchip Linux 方案的存储布局如下表所示（Android 方案除 boot / rootfs 定义有差异外，其他基本一致，可参考借鉴）。

| 分区 | 起始扇区 | 扇区数 | 大小 | GPT PartNum | 说明 |
|------|----------|--------|------|-------------|------|
| MBR | 0 | 1 | 512B (0.5KB) | - | - |
| Primary GPT | 1 | 63 | 32256B (31.5KB) | - | - |
| loader1 | 64 | 7104 | 4096000B (2.5MB) | 1 | Preloader（Miniloader 或 U-Boot SPL） |
| Vendor Storage | 7168 | 512 | 262144B (256KB) | - | SN, MAC 等 |
| Reserved Space | 7680 | 384 | 196608B (192KB) | - | 未使用 |
| reserved1 | 8064 | 128 | 65536B (64KB) | - | Legacy DRM Key |
| U-Boot ENV | 8128 | 64 | 32768B (32KB) | - | - |
| reserved2 | 8192 | 8192 | 4194304B (4MB) | - | Legacy Parameter |
| loader2 | 16384 | 8192 | 4194304B (4MB) | 2 | U-Boot 或 UEFI |
| trust | 24576 | 8192 | 4194304B (4MB) | 3 | Trusted-OS（ATF, OP-TEE） |
| boot（可引导） | 32768 | 229376 | 117440512B (112MB) | 4 | Kernel, DTB, extlinux.conf, Ramdisk |
| rootfs | 262144 | - | - | 5 | Linux 系统 |
| Secondary GPT | 16777183 | 33 | 16896B (16.5KB) | - | - |

> 引用来源：<http://opensource.rock-chips.com/wiki_Partitions>

### 4.2 分区表（Partition Table）

Rockchip U-Boot 支持两种分区表格式：

- **RK Parameter 格式**（旧）
- **标准 GPT 格式**（新）

当机器上同时存在两种分区表时，**优先使用 GPT 分区表**。无论是 GPT 还是 RK Parameter，烧写用的分区表文件都叫 `parameter.txt`。用户可通过 `TYPE: GPT` 属性确认是否为 GPT 格式：

```
FIRMWARE_VER:8.1
MACHINE_MODEL:RK3399
MACHINE_ID:007
MANUFACTURER: RK3399
MAGIC: 0x5041524B
ATAG: 0x00200800
MACHINE: 3399
CHECK_MASK: 0x80
PWR_HLD: 0,0,A,0,1
TYPE: GPT                               // 当前是 GPT 格式的分区表，否则为 RK Parameter
CMDLINE:mtdparts=rk29xxnand:0x00002000@0x00004000(uboot),......
```

### 4.3 设备别名（Aliases）

U-Boot 中有些特殊的 Aliases 有别于 Kernel DTS 里的定义。eMMC 和 SD 在 U-Boot 中统称为 **mmc** 设备，使用编号 0、1 区分。**SD 的启动优先级高于 eMMC**：

```
mmc1：表示 SD 卡
mmc0：表示 eMMC
```

### 4.4 Vendor Storage

Rockchip U-Boot 提供了 Vendor Storage 区域给用户保存 SN、MAC 等信息。存储偏移定义如下（详见 `vendor.c`）：

```
#define EMMC_VENDOR_PART_OFFSET      (1024 * 7)
/* --- Spi Nand / SLC / MLC 大容量场景 --- */
#define NAND_VENDOR_PART_OFFSET      0
/* --- Spi / Spi Nand / SLC / MLC 小容量场景 --- */
#define FLASH_VENDOR_PART_OFFSET     8
......
```

> 用户一般不需要关注和修改存储偏移，只需关注读写接口。

**读写接口**：

```
int vendor_storage_read(u16 id, void *pbuf, u16 size);
int vendor_storage_write(u16 id, void *pbuf, u16 size);
```

## 五、固件与镜像

### 5.1 Kernel 镜像格式（Image Kernel）

Rockchip U-Boot 支持三种格式的内核固件引导，引导优先级为：**Android > RK > Distro**。每一类固件都有对应的启动命令，三个命令按优先级逐个执行，直到固件被引导起来。如果所有命令都失败，则停留在 U-Boot 命令行模式。

启动优先级定义：

```
#define RKIMG_BOOTCOMMAND \
    "boot_android ${devtype} ${devnum};" \
    "bootrkp;" \
    "run distro_bootcmd;"
```

#### RK 格式

镜像文件的 magic 为 `"KRNL"`：

- `kernel.img` = Kernel
- `resource.img` = DTB + logo.bmp + logo_kernel.bmp
- `boot.img` = Ramdisk
- `recovery.img` = Ramdisk（for recovery）

```
00000000  4B 52 4E 4C 42 97 0F 00 1F 8B 08 00 00 00 00 00   KRNL...........
00000010  00 03 A4 BC 0B 78 53 55 D6 37 BE 4F 4E D2 A4 69   .....xSU.7.ON..i
```

#### Android 格式

镜像文件的 magic 为 `"ANDROID!"`：

- `boot.img` = Kernel + Ramdisk + Resource + `<dtb>`
- `recovery.img` = Kernel + Ramdisk（for recovery）+ Resource + `<recovery_dtbo>` + `<dtb>`

```
00000000  41 4E 44 52 4F 49 44 21 24 10 74 00 00 80 40 60   ANDROID!$.t...@`
00000010  F9 31 CD 00 00 00 00 62 00 00 00 00 00 00 F0 60   .1.....b.......`
```

> - `recovery_dtbo`：从 Android 9.0 才开始新增的镜像
> - `dtb`：从 Android 10.0 才开始新增的镜像

#### Distro 格式

目前开源 Linux 的一种通用固件打包格式：将 Ramdisk、DTB、Kernel 打包成一个镜像。这个镜像通常以某种文件系统格式存在（例如 ext2、ext4、FAT 等），U-Boot 需要通过文件系统才能访问其内容。

更多参考：

```
./doc/README.distro
./include/config_distro_defaults.h
./include/config_distro_bootcmd.h
```

### 5.2 U-Boot 镜像格式（Image U-Boot）

Rockchip U-Boot 和 Trust 有两种固件格式：**RK 格式**和 **FIT 格式**，分别由 Miniloader 和 SPL 负责引导。

目前 Rockchip 发布的 SDK 以 **RV1126** 为分界点：
- RV1126 **之前**的平台：采用 **RK 格式**
- RV1126 **开始**的平台：采用 **FIT 格式**

#### RK 格式

Rockchip 自定义的固件格式，U-Boot 和 Trust 分别打包为 `uboot.img` 和 `trust.img`：

- `uboot.img` 和 32 位 `trust.img` 的 magic 为 `"LOADER"`
- 64 位 `trust.img` 的 magic 为 `"BL3X"`

```
// uboot.img / 32 位 trust.img
00000000  4c 4f 41 44 45 52 20 20 00 00 00 00 00 00 00 00   LOADER  ........
00000010  00 00 20 00 78 d0 0f 00 06 99 c2 a8 20 00 00 00   .. .x....... ...
00000020  09 8a b0 e1 89 7a c2 89 0d e8 da ef 86 3e f2 24   .....z......>.$

// 64 位 trust.img
00000000  42 4c 33 58 00 01 00 00 23 00 00 00 f8 00 04 00   BL3X....#.......
00000010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00   ................
```

#### FIT 格式

U-Boot mainline 支持的一种灵活性极高的固件格式。U-Boot、Trust 以及 MCU 等固件一起打包为 `uboot.img`。

镜像文件的 magic 为 `"d0 0d fe ed"`，使用 `fdtdump uboot.img` 可查看固件头。

```
00000000  d0 0d fe ed 00 00 06 00 00 00 00 58 00 00 04 c4   ...........X....
00000010  00 00 00 28 00 00 00 11 00 00 00 10 00 00 00 00   ...(............
```

> 更多 FIT 格式介绍请参考 FIT 章节。

#### 备份打包

为了应对 OTA 升级过程中断电等可能导致固件损坏的情况，`uboot.img` 和 `trust.img` 都做了多备份打包。从分区表可知，`uboot.img` 和 `trust.img` 的大小默认都是 **4MB**。

**修改单份大小和份数的方法**：

- **RK 格式**：编译命令追加参数，例如 `--sz-uboot 2048 1` 和 `--sz-trust 4096 1`，表示 `uboot.img` 单份 2MB、打包 1 份；`trust.img` 单份 4MB、打包 1 份
- **FIT 格式**：更改配置参数 `CONFIG_SPL_FIT_IMAGE_KB`（单份大小，单位 KB）和 `CONFIG_SPL_FIT_IMAGE_MULTIPLE`（打包份数）

| 固件 | 单份大小 | 打包份数 |
|------|----------|----------|
| RK `uboot.img` | 1MB | 4 |
| RK 32 位 `trust.img` | 1MB | 4 |
| RK 64 位 `trust.img` | 2MB | 2 |
| FIT `uboot.img` | 2MB | 2 |

### 5.3 镜像解压（Image Decompress）

64 位平台通常烧写 Image，由 U-Boot 加载到目标运行地址。Rockchip U-Boot 还额外支持对 64 位 **LZ4 格式**的压缩内核进行解压。

需要使能：

```
CONFIG_LZ4=y
```

64 位 LZ4 压缩内核的解压前、后地址必须在各平台的 `rkxxx_common.h` 文件中定义：

```
#define ENV_MEM_LAYOUT_SETTINGS \
    "scriptaddr=0x00500000\0" \
    "pxefile_addr_r=0x00600000\0" \
    "fdt_addr_r=0x01f00000\0" \
    "kernel_addr_no_bl32_r=0x00280000\0" \
    "kernel_addr_r=0x00680000\0" \   // LZ4 解压内核的地址
    "kernel_addr_c=0x02480000\0" \   // LZ4 压缩内核的地址
    "ramdisk_addr_r=0x04000000\0"
```

> **32 位平台说明**：通常烧写 `zImage`，由 U-Boot 加载到 `kernel_addr_r` 地址，再由内核完成自解压。但 Rockchip U-Boot 还可支持 Image 格式，由 U-Boot 加载到目标运行地址。目前各平台的 `rkxxx_common.h` 只定义了 `kernel_addr_r` 而没有定义 `kernel_addr_c` 地址。用户不需要更改配置，U-Boot 会自动判断是 zImage 还是 Image，动态处理这两个地址。**但必须关闭 `CONFIG_SKIP_RELOCATE_UBOOT`**。

32 位内核加载地址定义：

```
#define ENV_MEM_LAYOUT_SETTINGS \
    "scriptaddr=0x60000000\0" \
    "pxefile_addr_r=0x60100000\0" \
    "fdt_addr_r=0x68300000\0" \
    "kernel_addr_r=0x62008000\0" \   // zImage 压缩内核的地址
    "ramdisk_addr_r=0x6a200000\0"
```

## 六、调试与高级特性

### 6.1 调用栈回溯（Stacktrace）

原生 U-Boot 不支持调用栈回溯机制，Rockchip 平台增加了该功能。目前有 3 种方式触发调用栈打印：

1. 系统崩溃时**自动触发**
2. 用户主动调用 `dump_stack()`
3. 使能 `CONFIG_ROCKCHIP_DEBUGGER`

**示例——系统 abort：**

```
"Synchronous Abort" handler, esr 0x96000010

// Abort 原因、PC、LR、SP
* Reason: Exception from a Data abort, from current exception level
* PC = 000000000028f430
* LR = 00000000002608d0
* SP = 00000000f3dceb30

...

// 重点突出 PC 和 LR
Call trace:
    PC: [< 0028f430 >]
    LR: [< 002608d0 >]

// 函数调用关系
Stack:
        [< 0028f430 >]
        [< 0028da24 >]
        [< 00211600 >]
        [< 002117b0 >]
        [< 00202910 >]
        [< 00202aa8 >]
        [< 0027698c >]
        [< 002151ec >]
        [< 00201b2c >]

// 指导用户转换上述调用栈信息
Copy info from "Call trace..." to a file(eg. dump.txt), and run
command in your U-Boot project: ./scripts/stacktrace.sh dump.txt
```

用户根据提示，将调用栈信息复制到任意 txt 文件（如 `dump.txt`）后执行：

```
cjh@Ubuntu:~/u-boot$ ./scripts/stacktrace.sh dump.txt

// 符号表来源

// 重点列出 PC 和 LR 对应的代码位置
Call trace:
    PC: [< 0028f430 >] strncpy+0xc/0x20 ./lib/string.c:98
    LR: [< 002608d0 >] on_serialno+0x10/0x1c ./drivers/usb/gadget/g_dnl.c:217

// 转换后得到真实函数名
Stack:
        [< 0028f430 >] strncpy+0xc/0x20
        [< 0028da24 >] hdelete_r+0xcc/0xf0
        [< 00211600 >] _do_env_set.isra.0+0x70/0x1b8
        [< 002117b0 >] env_set+0x3c/0x58
        [< 00202910 >] rockchip_set_serialno+0x54/0x140
        [< 00202aa8 >] board_late_init+0x5c/0xa0
        [< 0027698c >] initcall_run_list+0x58/0x94
        [< 002151ec >] board_init_r+0x20/0x24
        [< 00201b2c >] relocation_return+0x4/0x0
```

转换命令有三种，根据调用栈打印后的指导说明选用：

```
./scripts/stacktrace.sh ./dump.txt      # 解析来自 U-Boot 的调用栈
./scripts/stacktrace.sh ./dump.txt tpl  # 解析来自 TPL 的调用栈
./scripts/stacktrace.sh ./dump.txt spl  # 解析来自 SPL 的调用栈
```

> **注意**：执行该命令时，当前机器上的固件必须和当前代码环境匹配才有意义，否则会得到错误的转换结果。

### 6.4 系统复位（Reset）

- U-Boot 的复位和 Kernel 一样，最终需要陷入 Trust 中完成
- U-Boot 命令行模式支持与 Kernel 同样的 `reboot xxx` 命令（依赖于 Kernel DTS 中的定义）

### 6.5 Fuse / OTP

Rockchip 平台为了方便调试 Secure-Boot 功能，只需要对固件签名就能开启 Secure-Boot 模式（可不烧写 eFuse / OTP）。

Miniloader 会通过 U-Boot 向 Kernel 追加 cmdline 表明当前的 eFuse / OTP 使能是否已被烧写：

- `"fuse.programmed=1"`：开启了 Secure-Boot，eFuse / OTP 已被烧写
- `"fuse.programmed=0"`：开启了 Secure-Boot，eFuse / OTP 未被烧写
- cmdline 中无 `fuse.programmed`：未开启 Secure-Boot（Miniloader 不传递），或 Miniloader 太旧不支持传递

> U-Boot 需要包含如下提交：
> ```
> 83c9bd4 board: rockchip: pass fuse programmed state to kernel
> ```

### 6.6 热键调试（Hotkey）

Rockchip 平台提供串口组合键触发事件用于调试和烧写（如果无法触发请多尝试几次；启用 Secure-Boot 时无效）。

开机时**长按**对应组合键：

| 组合键 | 功能 |
|--------|------|
| Ctrl + C | 进入 U-Boot 命令行模式 |
| Ctrl + D | 进入 Loader 烧写模式 |
| Ctrl + B | 进入 Maskrom 烧写模式 |
| Ctrl + F | 进入 Fastboot 模式 |
| Ctrl + M | 打印 bidram / sysmem 信息 |
| Ctrl + I | 使能内核 initcall_debug |
| Ctrl + P | 打印 cmdline 信息 |
| Ctrl + S | "Starting kernel..." 之后进入 U-Boot 命令行 |

### 6.7 ATAGS 固件通信

Rockchip 平台的各级固件之间可以通过 **ATAGS** 机制传递配置信息。

- **适用范围**：DDR Bin、Miniloader、Trust、U-Boot（不包含 Kernel）
- **传递内容**：串口配置、存储类型、ATF 和 OP-TEE 占用的内存、DDR 容量等

**启动流程**：

```
BOOTROM => DDR Bin => Miniloader => TRUST => U-BOOT => KERNEL
```

**代码实现**：

```
./arch/arm/include/asm/arch-rockchip/rk_atags.h
./arch/arm/mach-rockchip/rk_atags.c
```

### 6.8 中断支持（Interrupt）

原生 U-Boot 没有完整支持中断，Rockchip 平台完善了该功能，支持 **GIC-V2** 和 **GIC-V3**。

> 更多参考：驱动模块章节。

### 6.9 SD 卡 / U 盘启动

Rockchip U-Boot 支持 SD 卡 / U 盘的固件启动或升级：

- **SD 启动 / 升级**：从 BOOTROM 这一级开始支持
- **U 盘启动 / 升级**：从 U-Boot 这一级开始支持

> 更多参考：系统模块章节。

### 6.10 Kernel DTB 机制

原生 U-Boot 只支持使用 U-Boot 自己的 DTB。Rockchip 平台增加了 **Kernel DTB 机制**，即使用 Kernel DTB 去初始化外设，主要目的是兼容外设板级差异（如 Power、Clock、Display 等）。

**二者的分工**：

| DTB | 职责 |
|-----|------|
| **U-Boot DTB** | 负责初始化存储、打印串口等设备 |
| **Kernel DTB** | 负责初始化存储、打印串口以外的设备 |

U-Boot 初始化时先用 U-Boot DTB 完成存储和打印串口初始化，然后从存储上加载 Kernel DTB，转而使用这份 DTB 继续初始化其余外设。Kernel DTB 的代码实现在函数 `init_kernel_dtb()`。

> 开发者一般不需要修改 U-Boot DTB（除非更换打印串口），各平台发布的 SDK 里使用的 `defconfig` 都已启用 Kernel DTB 机制。外设的 DTS 修改应该在 Kernel DTB 上进行。

**U-Boot DTB 编译机制**：启用 Kernel DTB 后，编译阶段会过滤出 U-Boot DTS 中带 `u-boot,dm-pre-reloc` 和 `u-boot,dm-spl` 属性的节点，再剔除 `defconfig` 中 `CONFIG_OF_SPL_REMOVE_PROPS` 指定的 property，最终生成 `u-boot.dtb` 并追加在 `u-boot.bin` 末尾。

**DTS 目录**：

```
./arch/arm/dts/
```

用户编译完 U-Boot 后可以用 `fdtdump` 命令检查 DTB 内容：

```
fdtdump ./u-boot.dtb | less
```

> 更多参考：进阶原理章节。

### 6.11 MMU / Cache

Rockchip 平台默认使能 MMU、D-Cache、I-Cache。MMU 采用 **1:1 线性映射**，D-Cache 采用 **Write-Back** 策略。

相关接口：

```
// I-Cache 接口
void icache_enable(void);
void icache_disable(void);
void invalidate_icache_all(void);

// D-Cache 接口
void dcache_disable(void);
void dcache_enable(void);
void flush_dcache_range(unsigned long start, unsigned long stop);
void flush_cache(unsigned long start, unsigned long size);
void flush_dcache_all(void);
void invalidate_dcache_range(unsigned long start, unsigned long stop);
void invalidate_dcache_all(void);

// 重新映射某块内存区间的 D-Cache 属性
void mmu_set_region_dcache_behaviour(phys_addr_t start, size_t size, enum dcache_option option);
```

### 6.12 HW-ID DTB（硬件识别设备树）

Rockchip U-Boot 可以根据 GPIO 或 ADC 的硬件状态，从多份 DTB 文件中筛选与硬件状态匹配的 DTB 进行加载。

> 更多参考：系统模块章节。
